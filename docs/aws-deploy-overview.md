# 今回の AWS デプロイ手順（全体像・手順ベース）

このドキュメントは、**在庫管理アプリを AWS にどのような順番でデプロイしたか**を、手順ベースで分かりやすくまとめたものです。詳細なコマンドは各リンク先のドキュメントを参照してください。

- **リージョン**: ap-northeast-1（東京）
- **最終形**: 1 つの URL（ALB）でフロント・バックエンド・RDS にアクセスし、admin / admin でログインできる

---

## デプロイの 3 段階

| 段階 | 内容 | 参照ドキュメント |
|------|------|------------------|
| **1. フロントを Fargate に載せる** | フロントだけを ECS Fargate で動かし、Public IP でアクセスできるようにする | `aws-ecs-fargate-deploy.md` |
| **2. RDS とバックエンドを追加** | DB を作り、バックエンドを Fargate で動かし、フロントから API でつなぐ | `aws-fargate-backend-db.md` |
| **3. ALB で 1 つの URL にまとめる** | ロードバランサーを前に立て、1 つの URL でフロントと API を振り分ける | `aws-alb-single-url.md` |

---

# 段階 1: フロントを Fargate に載せる

**目的**: フロントエンド（Vite）を ECS Fargate で動かし、ブラウザから「IP:5173」で開けるようにする。

## 手順の流れ

1. **変数を用意する**  
   アカウント ID・リージョン・VPC・サブネットなどを PowerShell の環境変数に設定する。

2. **ECR リポジトリを作る**  
   フロント用の Docker イメージを置く ECR リポジトリ（例: `inventory-ledger-app`）を作成する。

3. **Docker イメージをビルドして ECR に push する**  
   フロント用 Dockerfile でビルドし、ECR にログインして `latest` タグで push する。

4. **IAM ロールを用意する**  
   ECS が ECR からイメージを取得し、CloudWatch Logs に送るための `ecsTaskExecutionRole` を作成・アタッチする（既にあればスキップ）。

5. **セキュリティグループを作る**  
   フロントの待ち受けポート（5173）を開放した SG を 1 つ作成する。

6. **ECS クラスターを作る**  
   クラスター名（例: `inventory-cluster`）で ECS クラスターを 1 つ作成する。

7. **ロググループを作る**  
   CloudWatch Logs のロググループ（例: `/ecs/inventory-task`）を作成する。

8. **タスク定義を登録する**  
   Fargate 用のタスク定義（コンテナ名・ポート 5173・ECR イメージ URI・ログ設定）を登録する。

9. **サービスを作成する**  
   上記クラスターにサービス（例: `inventory-service`）を作り、タスクを 1 つ起動する。ネットワークは「パブリックサブネット＋Public IP 付与」。

10. **タスクの Public IP を取得して確認する**  
    起動したタスクに割り当てられた Public IP を取得し、ブラウザで `http://<IP>:5173` を開いてフロントが表示されることを確認する。

**この時点では** フロントだけが動いており、バックエンドや DB はまだありません（ログインはできない状態）。

---

# 段階 2: RDS とバックエンドを追加

**目的**: PostgreSQL（RDS）を作り、バックエンド（FastAPI）を Fargate で動かす。フロントの API 向き先をバックエンドの URL にし、ログインできるようにする。

## 手順の流れ

### RDS（データベース）の準備

1. **変数を用意する**  
   アカウント ID・リージョン・VPC・サブネットに加え、RDS のマスタパスワードなどを設定する。

2. **RDS 用セキュリティグループを作る**  
   RDS 用の SG を 1 つ作成する（この時点ではインバウンドは追加しない）。

3. **DB サブネットグループを作る**  
   RDS を置くための DB サブネットグループを、デフォルト VPC のサブネットで作成する。

4. **RDS インスタンスを作成する**  
   PostgreSQL 16、db.t3.micro、非公開、マスタユーザーと DB 名を指定して RDS を作成する。完了まで 5〜10 分かかる。

5. **RDS のエンドポイントを取得する**  
   作成した RDS のエンドポイント（ホスト名）を取得し、接続文字列をメモする（バックエンドの環境変数で使う）。

### バックエンドのデプロイ

6. **バックエンド用 ECR リポジトリを作る**  
   例: `inventory-ledger-backend`。

7. **バックエンド用セキュリティグループを作る**  
   ポート 8000 を開放した SG を作成する。

8. **RDS の SG に「バックエンド SG からの 5432」を許可する**  
   バックエンドタスクだけが RDS に接続できるようにする。

9. **バックエンドの Docker イメージをビルドして ECR に push する**  
   プロジェクトルートで `backend/Dockerfile` を使ってビルドし、ECR に push する。

10. **バックエンド用ロググループを作る**  
    例: `/ecs/inventory-backend-task`。

11. **バックエンドのタスク定義を作成する**  
    コンソールの JSON で作成するのが確実。  
    - イメージ: ECR の `inventory-ledger-backend:latest`  
    - 環境変数: `database_url`（async）、`database_url_sync`、`secret_key`、`cors_origins`（フロントの URL を入れる）  
    - ログ: 上記ロググループへ送る  

    `YOUR_ACCOUNT_ID`・`YOUR_RDS_ENDPOINT`・`YOUR_RDS_PASSWORD`・`YOUR_FRONTEND_URL` を実際の値に置き換える。

12. **バックエンドサービスを作成する**  
    クラスターにサービス（例: `inventory-backend-service`）を作り、Fargate で 1 タスク起動。パブリックサブネット＋Public IP。

13. **バックエンドの Public IP を取得する**  
    タスクが RUNNING になったら、バックエンドの Public IP を取得する（例: `http://<IP>:8000`）。

### フロントとバックエンドをつなぐ

14. **フロントのタスク定義を更新する**  
    新しいリビジョンで、環境変数 `VITE_API_URL` に「バックエンドの URL」（例: `http://<バックエンドのIP>:8000`）を設定する。

15. **フロントサービスを新リビジョンで再デプロイする**  
    `update-service` でタスク定義を新リビジョンにし、`--force-new-deployment` で再デプロイする。

16. **動作確認する**  
    フロントの URL（`http://<フロントのIP>:5173`）を開き、**admin / admin** でログインできることを確認する。

**注意**: バックエンドのタスクが再起動されると Public IP が変わるため、そのたびにフロントの `VITE_API_URL` を新しい IP に更新し直す必要があります。これを解消するのが次の「ALB で 1 URL にまとめる」です。

# 段階 3: ALB で 1 つの URL にまとめる

**目的**: Application Load Balancer（ALB）を前に立て、**1 つの URL**（例: `http://inventory-alb-xxx.ap-northeast-1.elb.amazonaws.com`）でフロントと API の両方にアクセスできるようにする。バックエンドの IP が変わっても URL は変わらない。

## 手順の流れ

1. **変数を用意する**  
   VPC・サブネット（2 つ）・既存のフロント/バックエンドサービスがある状態で、ALB 用の変数を設定する。

2. **ALB 用セキュリティグループを作る**  
   ALB 用の SG を作成し、インバウンドで TCP 80（HTTP）を 0.0.0.0/0 から許可する。

3. **ターゲットグループを 2 つ作る**  
   - **フロント用**: ポート 5173、ヘルスチェックパス `/`  
   - **バックエンド用**: ポート 8000、ヘルスチェックパス `/health`

4. **ALB を作成する**  
   上記 2 サブネット・ALB 用 SG で、internet-facing の Application Load Balancer を作成する。

5. **リスナー（ポート 80）を追加する**  
   デフォルトアクションを「フロント用ターゲットグループへ転送」にし、リスナーを作成する。

6. **パスルールを追加する**  
   条件「パスが `/api/*`」のときは「バックエンド用ターゲットグループへ転送」するルールを、上記リスナーに追加する。

7. **ALB の DNS 名を取得する**  
   これが「1 つの URL」のホスト名になる（例: `http://<ALB_DNS>`）。

8. **フロント・バックエンドの SG に ALB からのアクセスを許可する**  
   フロントの SG には ALB からの 5173、バックエンドの SG には ALB からの 8000 を許可する。

9. **ECS サービスにロードバランサーを紐付ける**  
   フロントサービスには「フロント用 TG・コンテナ app・ポート 5173」、バックエンドサービスには「バックエンド用 TG・コンテナ backend・ポート 8000」をそれぞれ `update-service` で設定する。必要に応じてタスク定義のポートが 5173 / 8000 になっているか確認する。

10. **フロントのタスク定義で VITE_API_URL を削除する**  
    1 つの URL にするため、API は同じオリジンの `/api` に送る。環境変数 `VITE_API_URL` を削除（または空）にした新しいリビジョンを作成する。

11. **バックエンドの CORS に ALB の URL を追加する**  
    タスク定義の `cors_origins` に `http://<ALB_DNS>` を追加した新しいリビジョンを作成し、サービスをそのリビジョンで更新する。

12. **バックエンドのイメージとコードを揃える**  
    バックエンドが `/api` プレフィックス付きで応答するようコード対応済みなら、必要に応じてイメージを再ビルドして ECR に push し、バックエンドサービスを再デプロイする。

13. **動作確認する**  
    ブラウザで **http://<ALB_DNS>** を開き、**admin / admin** でログインできることを確認する。  
    ターゲットが healthy になるまで 2〜5 分かかることがある。

**この時点で** 1 つの URL でフロントと API が使え、バックエンドの IP が変わっても URL は変わりません。HTTPS にしたい場合は `aws-alb-single-url.md` の「HTTPS 化」セクションを参照してください。

# まとめ（何をいつやったか）

| 順番 | やったこと | 結果 |
|------|------------|------|
| 1 | フロントを ECR に push し、ECS Fargate で 1 タスク起動 | `http://<フロントのIP>:5173` でフロントだけ表示（ログイン不可） |
| 2 | RDS（PostgreSQL）を作成 | DB が VPC 内で利用可能に |
| 3 | バックエンドを ECR に push し、ECS Fargate で 1 タスク起動。フロントの VITE_API_URL をバックエンドの IP に設定 | フロントからバックエンドに API で接続し、admin でログイン可能（バックエンドの IP が変わると設定し直しが必要） |
| 4 | ALB と 2 つのターゲットグループを作成し、パスで振り分け（`/` → フロント、`/api/*` → バックエンド）。両サービスを ALB に紐付け、フロントは VITE_API_URL 削除・バックエンドは CORS に ALB URL を追加 | **1 つの URL**（`http://<ALB_DNS>`）でフロント・API の両方にアクセス可能。IP 変動の影響なし |

詳細なコマンドや JSON は、それぞれ **aws-ecs-fargate-deploy.md**（段階 1）、**aws-fargate-backend-db.md**（段階 2）、**aws-alb-single-url.md**（段階 3）を参照してください。
